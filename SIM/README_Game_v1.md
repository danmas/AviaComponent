**Дата:** 2026-11-26

**Основа:** `README_Game_proposal.md` с правками по итогам обсуждения.
**Обфускация:** все имена — после обфускации. Заказчик и система — `Альфа-Пром`, проект — `Авиакомпонент`, подрядчики — `Кооператор-1`, `Кооператор-2`.

## Главный сдвиг относительно предложения

| | В предложении | В этой версии |
|---|---|---|
| Кто игрок | Мастер | **Руководитель** |
| Что главное на экране | Стык цех ↔ Система | **Главный экран руководителя** |
| Что проверяется | Дисциплина учёта | **Качество управленческих решений на неполных данных** |
| Роль цеха | Второй экран рядом | **За кадром**, вскрывается в разборе |
| Реестр достоверности | Не упомянут | **Центральная механика** |

**Причина сдвига.** Главный заказчик проекта — руководитель предприятия. Значит главный экран, который он уже видел в дорожной карте, — не «развитие после ТЗ», а основной интерфейс. Игра должна говорить на его языке.

**Главная асимметрия** переворачивается:

> Руководитель не видит цех. Он видит только Систему.
> Правда о цехе доступна ему лишь в разборе партии.

Это и есть предмет тренажёра: решения при неполных данных.

---

## Игровой цикл

Один цикл = одна смена.

```
1. Экран обновился
   ├─ 4 показателя
   └─ реестр достоверности: где покрытие низкое и почему

2. Решение (1–3 действия за смену)
   ├─ обещать срок заказчику (и какой)
   ├─ принять / отложить новую заявку
   ├─ усилить участок (сверхурочные, кооперация, перенос)
   ├─ отправить на проверку данных
   └─ изменить приоритет

3. Время идёт — цех работает (есть свой экран, см. раздел «Экраны»)
   ПДО планирует, мастер ставит отметки (с настраиваемой дисциплиной),
   ОТК бракует, станки ломаются

4. Последствия
   ├─ заказчик жалуется на срок
   ├─ участок простаивает
   ├─ срок сорван
   └─ показатель изменился, но не так, как ожидалось

5. Разбор смены
   что видел руководитель  ↔  что было в цехе
```

Цикл короткий: одна смена — один экран решений. Партия — 10–15 смен.

## Экран: состав

Собран по дорожной карте главного экрана (ноябрь 2026), чтобы заказчик узнал свой интерфейс.

### Четыре показателя

| Показатель | Что показывает | Из чего собирается |
|---|---|---|
| **Портфель заявок** | Сколько заявок в работе и на какую сумму н/ч | заявки + нормы |
| **Перегрузка участков** | Какие участки выше мощности | план / мощность смены |
| **Принято за смену** | Сколько операций закрыто | отметки мастеров |
| **Риск сроков** | Какие заявки под угрозой | расчётная дата против договорной |

### Блоки

| Блок | Содержание |
|---|---|
| **Мощность и загрузка** | По участкам: мощность, план, очередь, % загрузки |
| **Итог смены** | План / факт / вне задания — по участкам и мастерам |
| **Что мешает по заявкам** | Топ причин: нет материала, нет КД, нет нормы, занят станок |
| **Проработка заявок** | Воронка: черновик → в ДСЕ → в производстве → архив |
| **Реестр достоверности** | По каждому показателю: покрытие, причина пробела, кто закрывает, что сделать |

### Реестр достоверности — как это работает в игре

Каждый показатель несёт **покрытие** — долю записей, на которых он реально собран.

| Покрытие | Что означает для решения |
|---|---|
| 90–100% | можно опираться |
| 60–89% | опираться можно, но с оговоркой |
| 30–59% | **рискованно** — решение может быть построено на дыре |
| < 30% | показатель недостоверен, решение — лотерея |

Руководитель видит покрытие **до** принятия решения. Это и создаёт конфликт: он знает, что данные плохие, но решение принимать надо.

**Пример конфликта.** Показатель «риск сроков» имеет покрытие 28% — у 72% заявок не заполнена договорная дата. Обещать срок заказчику можно, но риск сорвать высок. Проверка данных займёт смену — и это смена без решения по заявке.

## Решения и их цена

Каждое решение имеет цену и последствие. Без этого игра — не игра.

| Решение | Плюс | Цена / риск |
|---|---|---|
| Обещать ранний срок | заказ принят, портфель растёт | при покрытии < 60% — высокий шанс сорвать |
| Обещать поздний срок | низкий риск срыва | заказчик может уйти |
| Принять заявку сверх мощности | выручка | очередь растёт, существующие сроки под угрозой |
| Отложить заявку | сохраняет выполнимость плана | потеря заказа |
| Сверхурочные на участке | +мощность сейчас | дорого, дисциплина падает |
| Кооперация (`Кооператор-1/2`) | снимает перегрузку | срок + стоимость + внешняя зависимость |
| Отправить на проверку данных | покрытие растёт | смена без продвижения по заявкам |
| Сменить приоритет | срочное закрыто | ранее начатая партия встала |

## Сценарии (уровни)

По возрастанию помех, как в предложении. Дисциплина — параметр поведения мастеров.

| Уровень | Данные | Что проверяется |
|---|---|---|
| **1. Чистые отметки** | покрытие ~95%, отметки сразу | работает ли сам алгоритм — базовая линия |
| **2. Поздние отметки** | отметка через смену | экран отстаёт от цеха, решения запаздывают |
| **3. Бумага** | 30–40% маршрута вне Системы | дыра в плане, доля ЭДО падает |
| **4. Пустые поля** | нет нормы / материала / даты | Система обязана оставить «не готово», а не рисовать срок из пустоты |

Отдельные сценарии-помехи поверх любого уровня:

- **срочный заказ** — в MVP, это суть работы руководителя
- **поломка станка** — мощность падает внезапно
- **брак и отрывная карта** — отрыв по ведомости дефекта не уменьшает количество родителя
- **смешение единиц** — н/ч, станко-часы, календарные часы как помеха чтения

## Экраны: три слоя видимости

Основная идея игры — проверить, **как модель Системы работает на модели Предприятия**. Для этого нужны экраны всех трёх уровней, а не только главный.

| Слой | Экран | Что показывает | Роль |
|---|---|---|---|
| **1. Предприятие (реальность)** | **Цех** | Участки, станки, что физически где стоит, кто чем занят, реальная загрузка | наблюдение / мастер |
| **2. Система (записи)** | **Рабочие места ролей** | Что каждая роль видит и вносит: заявка, ТП, норма, план, отметка, ОТК | коммерсант, технолог, нормировщик, ПДО, мастер, рабочий, ОТК |
| **3. Система (свод)** | **Главный экран руководителя** | 4 показателя, 5 блоков, реестр достоверности | руководитель |

Ни один слой не подменяет другой. **Главный экран не показывает цех, а цех не показывает записи.** Расхождение между ними — предмет игры.

### Экран цеха (реальность)

Обязателен: без него нельзя увидеть, что Система работает не на истине, а на записях.

| Блок | Содержание |
|---|---|
| Участки | Список участков с типом ресурса: станки, печи, персонал, кооперация |
| Загрузка в реальности | Сколько станков занято, сколько простаивает, длина физической очереди |
| Что где стоит | Партии на участке: сколько деталей, на какой операции, сколько лежит |
| Кто чем занят | Рабочие и мастера: на какой операции, с какого времени |
| Простои | Станок стоит без работы — и по какой причине (нет материала, нет задания, поломка) |
| Журнал цеха | Что физически произошло: операция закрыта, брак, поломка, передача |

Экран цеха — **не** часть Системы. Он показывает то, чего в Системе может не быть вовсе: операцию сделали и не отметили, деталь лежит и ждёт, станок простаивает без записи.

### Рабочие места ролей (записи)

Роли из ТЗ, раздел 2, и из описания системы. Каждая вносит свою часть данных — и именно из них собираются своды.

| Роль | Экран | Что вносит | Что видит |
|---|---|---|---|
| **Коммерческий отдел** | Заявка | Заказчик, номенклатура, количество, срок, приоритет; прикрепление требований, чертежей, спецификаций | Журнал заявок, статусы, портфель |
| **Технолог** | Техпроцесс | Маршрут операций, согласование ТП, версии; ИИ-технолог как черновик | Дерево изделия, КД, нормы по операциям |
| **Нормировщик** | Нормирование | н/ч и ПЗВ по операциям | Справочник норм, материалы, формулы |
| **ПДО** | Пульт планирования | Приоритеты, распределение по участкам, сменные задания | Очередь, загрузка по плану, расчётный срок |
| **Мастер** | Задание участка | Отметки: взял / сдал / брак; закрытие операции | Задания на смену, люди участка |
| **Рабочий** | Терминал | Отметка начала и конца операции, количество | Своё задание |
| **ОТК** | Контроль | Приёмка, дефекты, решения по браку, карты замеров | Партии на контроль, ведомости дефектов |
| **Архивариус** | Архив КД | Проверка и привязка документации | Чертежи «КД для производства» |
| **Кладовщик** | Склад | Приход, резерв, выдача материала, отгрузка ГП | Остатки, резервы |

### Как связаны слои

```
ЦЕХ (реальность)          РОЛИ (записи)              РУКОВОДИТЕЛЬ (свод)
─────────────────         ─────────────────          ────────────────────
деталь стоит на   ──?──►  мастер отметил    ──?──►   «на операциях 1 533»
участке                   (или не отметил)
станок занят      ──?──►  задание закрыто   ──?──►   «загрузка 96%»
партия ушла       ──?──►  ОТК принял        ──?──►   «принято за смену 42»
```

Знак `──?──` — не стрелка, а **вопрос**. Каждый переход может не состояться: не отметили, отметили позже, отметили на бумаге, отметили неверно. Игра и показывает, что происходит со сводом, когда переход рвётся.

### Что видит игрок-руководитель и чего не видит

| Доступно руководителю | Скрыто до разбора |
|---|---|
| Показатели и их покрытие | Фактические даты операций |
| Загрузка участков по плану | Реальная занятость станков |
| Расчётные сроки | Когда деталь реально легла на склад |
| Очередь по участкам | Сколько операций сделано вне задания |
| Число отмеченных операций | Сколько сделано и не отмечено |
| Жалобы заказчиков | Причина: брак, простой или ошибка плана |

**Правило:** любая цифра на экране существует ровно в той мере, в какой её собрали отметки. Наличие показателя подтверждает отображение, а не точность.

### Переключение слоёв

Игрок-руководитель может в любой момент переключиться на экран цеха или на рабочее место любой роли.

| Режим | Смысл |
|---|---|
| **Только свод** (по умолчанию) | честный режим: видно ровно то, что видит руководитель |
| **Свод + цех** | режим наблюдения: рядом реальность и записи, расхождение видно сразу |
| **Любая роль** | режим разбора: понять, откуда взялась или не взялась запись |

Это не меняет исход партии — меняет только понимание. Для демо заказчику важны все три: в первом он узнаёт свою боль, во втором видит её причину, в третьем — место, где её чинить.

## Разбор партии

Главный экран после партии. Не очки, а сопоставление.

| Колонка | Содержание |
|---|---|
| Решение | что сделал руководитель и когда |
| Основание | какой показатель и какое покрытие были на экране |
| Что было в цехе | факт по скрытой модели |
| Итог | подтвердилось / разошлось / невозможно проверить |

### Журнал решений → требования к Системе

Каждое расхождение даёт формулировку требования. Это мост от игры к ТЗ.

| Ситуация в игре | Требование к Системе |
|---|---|
| Обещал срок по показателю с покрытием 28% → сорвал | Блокировать обещание срока при покрытии ниже порога, либо явно запрашивать подтверждение |
| План пересчитался, но версии нет — сравнить нельзя | **Хранить версию плана** (закрывает противоречие 03) |
| Правило «узкое место» отобрало 6 из 26 участков непонятно почему | Раскрывать критерий отбора узкого места (Н09) |
| Отметка пришла через смену — экран врал | Требование к своевременности отметки + метрика запаздывания |
| Операция в плане без нормы | Блокировать планирование без нормы (зона «не готово») |
| Единицы смешались | Легенда единиц на экране (закрывает зону А5) |

## Модель предприятия

Предприятие не «за кадром» — у него есть свой экран (см. «Экраны: три слоя видимости»). Но данные из него попадают в Систему **только через людей**, и каждый переход может не состояться.

Упрощена до минимума, но правила — из документов. Агенты цеха работают автоматически, их поведение настраивается уровнем сложности.

### Этапы (из «ИТ-процессы», ноябрь 2026)

| № | Этап | Периодичность |
|---|---|---|
| 1 | Заявка (письмо, заказчик, срок) | раз на заявку |
| 2 | Структура изделия и КД | раз на заявку |
| 3 | Техпроцесс и согласование | раз на заявку |
| 4 | Нормирование (н/ч, ПЗВ) | раз на заявку |
| 5 | Обеспечение материалом | раз на заявку |
| 6 | Планирование | по каждой партии |
| 7 | Запуск и движение по операциям | по каждой партии |
| 8 | Контроль качества | по каждой партии |
| 9 | Сборка, склад ГП, отгрузка | по каждой партии |

### Участки — из реконструкции карты

Не выдуманные. Маршрут MVP собран из участков, реально присутствующих на карте потоков предприятия:

```
Токарная ЧПУ → Фрезерная → Термообработка → Слесарная → Испытательная → Окончательный контроль → Склад ГП
```

Пропорции ожидания и нормы — по порядку величины из тех же данных (например, на слесарной ожидание кратно превышает норму). Точные значения — модельные, помечаются как модельные.

**Типы ресурсов** (из описания системы): станки, печи, персонал, кооперация. Печь планируется садкой (сутки), станок — очередью, человек — сменой.

### Жизненный цикл объекта учёта

```
Заявка → Сборка → Деталь → Партия (запуск)
                              ├─ Деление / отрывная карта
                              ├─ Операции цеха (выполнено / брак / принято)
                              ├─ Приёмка ОТК
                              ├─ Окончательный контроль
                              ├─ Склад ГП
                              └─ Отгрузка → Архив заявки
```

### Агенты цеха (поведение настраивается)

| Агент | Поведение | Параметр |
|---|---|---|
| ПДО | планирует по норме, ставит в очередь, приоритет по сроку | качество плана |
| Мастер | берёт задание, делает, ставит отметку | **дисциплина**: сразу / через смену / на бумагу / пропуск |
| ОТК | принимает или бракует | доля брака |
| Коммерсант | приносит заявки | интенсивность потока |
| Станок | работает или ломается | MTBF |

Дисциплина мастера — **ключевой параметр уровня**. Он и создаёт разрыв между экраном и цехом.

## Что даёт демо заказчику

| Что он видит | Что понимает |
|---|---|
| Свой главный экран, свои 4 показателя | «это мой интерфейс» |
| Покрытие 28% у показателя «риск сроков» | «данные, которыми я управляю, дырявые» |
| Решение по дырявым данным → срыв | «вот почему сроки не сходятся» |
| Переключение в мастера: операция сделана, не отмечена | «вот где теряется факт» |
| Разбор: план пересчитался, версии нет | «вот почему нельзя сравнить план с фактом» |
| Журнал решений → требования | «вот что нужно доработать в Системе» |

**Главный результат демо:** руководитель перестаёт спрашивать «почему система врёт» и начинает спрашивать «что нужно, чтобы она не врала». Это и есть переход от претензии к ТЗ.

## Технический контур

| Слой | Решение | Причина |
|---|---|---|
| Язык | TypeScript, один процесс | как принято на этом стенде, без синхронизации двух сред |
| Модель | событийная очередь по времени | домен — операции в часах и днях, DES избыточен |
| Детерминизм | seeded RNG | эксперимент должен воспроизводиться |
| UI | React + SVG | нужна схема потоков, не 3D |
| Разделение | модель предприятия и модель Системы — разные модули, обмен событиями | нельзя делить состояние, иначе проверка теряет смысл |

## Открытый вопрос

Формулировка из предложения заменена под новую главную роль.

**Было:**
> Совпадает ли срок маршрутного листа с цехом, и как быстро экран расходится при опоздании мастера.

**Стало:**
> **Может ли руководитель за 10–15 смен принимать решения не хуже, чем при полных данных, — и что должно появиться на экране, чтобы это стало возможно?**

Второй вопрос ближе к заказчику и прямо порождает требования к Системе.

### Из чего складывается ответ

| Срез демо | Что показывает |
|---|---|
| Партия на полных данных | потолок: как выглядит работа при покрытии ~95% |
| Та же партия при покрытии 30% | деградация: сколько решений оказываются ошибочными |
| Разбор решений | какие именно решения ломаются первыми, когда данных мало |
| Журнал → требования | что должно появиться на экране, чтобы деградация исчезла |

> Если при полных данных руководитель тоже ошибается — проблема не в достоверности, а в самом алгоритме планирования. Игра это покажет, и это отдельный вывод для ТЗ.
