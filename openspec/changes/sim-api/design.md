## Context

См. [proposal.md](proposal.md). Замеры, определившие решения ниже (стенд `clean`/`none`, seed 42, горизонт 12 смен):

| Замер | Значение |
|-------|----------|
| Полный прогон 12 смен | 0.7–1.2 мс |
| Прогон 120 смен | 14.7 мс |
| Префикс 0–5 смен при горизонте 6 против 12 | совпал, 20 событий |
| Пошаговый прогон (горизонт 1…12) против полного | расхождений нет |
| `PlantState` в JSON | 11.9 КБ |
| Закрытий по сменам | 3,6,4,2,3,2,3,2,3,2,3,2 — всего 37 |
| Сообщений `shift-completed` на горизонте | 12 |

Ключевое: точки «прогнать одну смену» в ядре нет — `runStand` проходит весь горизонт за вызов. Но префикс устойчив и прогон стоит 1 мс, значит шаг смены делается перепрогоном с горизонтом `N+1`.

## Goals / Non-Goals

**Goals**

- Через HTTP получить срез, отдать решение и продвинуть смену — без UI.
- Один и тот же контракт для React, CLI и тестов.
- Ядро не знает про HTTP: сервер вызывает `runStand` и сериализует.
- Срез цеха недоступен клиенту руководителя без явного запроса.

**Non-Goals**

- Аутентификация, мультиплеер, сохранение сессий в БД.
- Копирование живого экрана пиксель в пиксель.
- Изменение правил модели производства и ёмкостей.
- Рабочие места ролей и разбор с вердиктами (этап 5).
- Остальные семь решений (этап 3c).

## Decisions

### D1. Шаг смены — перепрогон с отсечкой, а не пошаговый цикл в цехе

**Решение.** `POST /sessions/:id/advance` увеличивает `currentShift` на единицу и выполняет `runStand` с горизонтом `currentShift + 1` и решениями, у которых `appliedAt <= currentShift * SHIFT_MINUTES`. Клиенту отдаётся срез на эту границу.

**Почему.** `runShop` не имеет точки останова: он идёт до `horizonEnd` в одном цикле `while`. Пошаговый движок потребовал бы вынести часы наружу и сохранять `jobs`/`busy`/`repairOpened` между вызовами — это переделка цеха без выигрыша. Замер: перепрогон 12 раз стоит 8–14 мс, префикс совпадает на всех границах 1…12.

**Цена.** O(N²) по горизонту. На горизонте стенда 10–15 смен это 15–25 мс на сессию. Кеш не вводится: ключ `(seed, level, overlay, решения до N)` даёт экономию, но сначала нужно доказать, что узкое место — прогон, а не сеть.

**Ограничение горизонта.** `runStand` не принимает горизонт аргументом — он читает `CONTRACT_STAND.horizonShifts` в 7 местах. Чтобы шаг смены заработал, эти места обязаны перейти на аргумент. Это правка ядра, и она входит в этап 3a, а не подразумевается.

### D2. Сессия — параметры прогона плюс решения, не изменяемое состояние цеха

**Решение.** Сессия хранит `id`, `seed`, `level`, `overlay`, `horizonShifts`, `currentShift`, `decisions[]`, `createdAt`, `journal[]`. `PlantState` и `SystemRecords` в сессии **не хранятся** — они результат прогона и пересчитываются.

**Почему.** Если хранить `PlantState` и позволять его менять, появится второй источник истины рядом с `runStand`, и детерминизм станет недоказуем. Прогон восстанавливается из параметров побайтово — это уже требование этапа 2.

**Следствие.** Перезапуск сервера убивает сессии, но не делает их невосстановимыми: клиент может пересоздать сессию из тех же `seed`/`level`/`overlay`/`decisions` и получить то же состояние. Это записывается в ответе `GET /sessions/:id` полем `replayable: true`.

**Что всё же хранится.** `journal[]` — выданные срезы и события с их `seq`. Он нужен для восстановления пропущенных событий после обрыва (D6) и для проверки «прошлый срез не изменился». Журнал — не состояние цеха: он только фиксирует, что уже было отдано клиенту.

### D3. Горизонт — параметр стенда, а не свободный параметр сессии

**Решение.** `horizonShifts` в сессии принимается, но проверяется `assertStandInSpec`: 10–15. Попытка выйти за диапазон — `400`, а не молчаливое ограничение.

**Почему.** В ядре `horizonShifts` — константа `CONTRACT_STAND`, зашитая в 7 местах `runStand` и охраняемая проверкой диапазона. Свободный горизонт — это изменение `CONTRACT_STAND`, то есть отдельный этап с перегенерацией фикстур. Держать его в API как «любое число» нельзя: обещание, которое ядро не выполнит.

### D3a. Мощность участка сервер не считает и не приводит

**Решение.** `capacity` в срезе приходит из `AreaLoadRecord` как есть, со своей единицей (`machine-hour`, `person-hour`, `charge-day`). Сервер не переводит единицы и не подставляет «12 часов смены».

**Почему.** Замер: `capacityOf` в `SIM/run/run.ts:129` зашивает 12 станко-часов, 12 человеко-часов и 0.5 суток садки — это функция сборки прогона, не параметр стенда в `CONTRACT_STAND`. Если сервер начнёт считать мощность сам, появится второе место с тем же правилом, и расхождение будет молчаливым. В срезе шесть участков, а не семь: склад ГП не участок загрузки.

### D4. Три среза по существующему контракту

**Решение.** `GET /sessions/:id` отдаёт только `summary` (четыре показателя + покрытие + реестр достоверности). `GET /sessions/:id/shop` отдаёт `shop` — и только он. `GET /sessions/:id/roles` отдаёт `roles`. Формы ответов типизированы типами из `SIM/contract/slices.ts`: `SummarySlice`, `ShopSlice`, `RoleRecordsSlice`.

**Почему.** Асимметрия «руководитель не видит цех» уже выражена в контракте (`LAYERS = ['shop','roles','summary']`, `ShopSlice` не входит в свод). Сервер не вводит нового правила видимости — он раздаёт готовые срезы по разным маршрутам.

**Правило.** Срез `shop` не попадает ни в один ответ, который клиент получает без явного запроса. Проверяется тестом: в ответе `GET /sessions/:id` нет поля `operations`.

### D5. Решение принимается только на текущую смену и только вперёд

**Решение.** `POST /sessions/:id/decisions` принимает `{ type, batchId, rank }` и присваивает `appliedAt = currentShift * SHIFT_MINUTES`. Решение с `appliedAt` в прошлом отклоняется `409`. Повторное решение по той же партии допускается и перекрывает прежнее **с этого момента** — прошлое не пересчитывается.

**Почему.** Это правило из `sim-priority-decision` D1–D2, перенесённое в API. Без проверки `appliedAt` клиент мог бы попросить переписать историю, а сервер обязан отказать, а не сделать вид.

### D6. WebSocket для шага, HTTP для остального

**Решение.** Управление сессией и снимки — HTTP. Шаг смены (`advance`) и подписка на события — WebSocket `GET /sessions/:id/stream`. События: `shift-started`, `shift-completed`, `metrics-updated`, `decision-applied`, `session-finished`.

**Почему.** Шаг — единственная операция, у которой есть длительность и поток результата. Держать её в HTTP при 1 мс прогона смысла нет, но WS даёт клиенту порядок событий без поллинга, и UI не придётся опрашивать.

**Формат.** Каждое сообщение — `{ seq, at, type, payload }`, где `seq` растёт монотонно в пределах сессии. Клиент, потерявший соединение, продолжает с `lastSeq` и получает пропущенные события из журнала сессии.

### D7. Fastify, а не Express

**Решение.** Fastify + `@fastify/websocket`, схемы JSON для валидации тела и ответа.

**Почему.** Схемы дают валидацию и сериализацию из одного описания; типы Fastify строже. Express потребовал бы отдельного валидатора.

### D8. Порт 3400 и запрет на смену порта из окружения

**Решение.** Порт по умолчанию 3400, переопределяется `SIM_API_PORT`. Проверка занятости — при старте, с внятным сообщением.

**Почему.** Замер: 3000, 3001, 3002, 3006, 3010 заняты (Kosmos Panel и др.). Молчаливый сдвиг порта сломал бы клиентов.

## Risks / Trade-offs

- [Перепрогон на каждую смену дорожает квадратично] → измерено: 15–25 мс на сессию горизонта 12. Кеш не вводится до доказанной необходимости.
- [Сессии теряются при рестарте сервера] → `replayable: true` и параметры в ответе позволяют пересоздать. Для тренажёра приемлемо; в БД — если появится требование.
- [Схема решения закрепляет только приоритет] → остальные семь типов добавятся как новые значения `type` с `400` на неизвестный. Схема не ломается, но v1 API умеет одно решение — это записывается в README.
- [WS-журнал растёт с горизонтом] → 12 смен × ~4 события = 48 записей на сессию. Не проблема; ограничение `lastSeq` окном не нужно.
- [Клиент может собрать картину цеха из `roles` и обойти асимметрию] → `roles` — это записи ролей, не состояние станков. Скрытое остаётся скрытым; проверяется тестом на отсутствие `operations` и `downtimes` в `summary` и `roles`.

## Migration Plan

Откат — удалить `SIM/api/` и зависимости. Ядро, фикстуры и отчёты не меняются. Этап обратно совместим: `npm test` без сервера работает как раньше.
