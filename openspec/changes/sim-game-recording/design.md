## Context

См. [proposal.md](proposal.md).

Прогон уже производит события контракта, старты и завершения операций, срезы на границах смен и решения руководителя. Этого достаточно, чтобы собрать след.

Цель следа — дать внешнему агенту и будущему UI возможность показать производство в движении: как заявки приходят, как рождаются партии, как детали идут от участка к участку и где задерживаются.

## Goals / Non-Goals

**Goals**

- След, по которому видно появление заявок, рождение партий и движение по маршруту в реальном времени.
- Два канала доставки:
  - **файл JSON** — для демонстрации внешнему агенту и для сохранения игры;
  - **API** — основной механизм, по которому работает UI игры.
- Детерминизм: тот же вход → тот же след.
- Обратная совместимость: обычный прогон не обязан писать след, если его не просили.

**Non-Goals**

- Новый игровой движок.
- Анимация внутри текущего бланкового UI.
- Запись сырого `PlantState` на каждый тик.
- Изменение правил очереди, садки или контроля.
- Явные стрелки `fromArea → toArea` (достаточно последовательности операций партии).

## Decisions

### D1. След — события на каждое значимое изменение + опорные кадры

**Решение.** След содержит:

- события на каждое движение:
  - заявка зарегистрирована;
  - партия создана;
  - операция стала готовой (`readyAt`);
  - ресурс взял операцию (`startedAt`);
  - операция закрыта (полностью или частично);
  - решение руководителя применено;
- опорные кадры на границах смен (свод + краткий цех).

**Почему.** Только границы смен не дают ощущения живого производства. События на каждое изменение позволяют UI анимировать движение деталей и рост/таяние очередей. Кадры смен остаются точками сверки и быстрой перемотки.

### D2. Время — минуты прогона

**Решение.** Все моменты — минуты от t0 (`SimInstant`).

**Почему.** Внешний агент и UI не должны знать внутренние детали смен. Смену можно вычислить.

### D3. Два канала: файл и API

**Решение.**

- Файл JSON (фикстура + возможность сохранить любой прогон) — для внешнего агента и для архива игры.
- `GET /v1/sessions/:id/trace` — для UI игры. Отдаёт тот же формат, что и файл.

**Почему.** Агенту нужен самодостаточный файл, который можно отдать без поднятого сервера. UI игры должен брать след у живой сессии через API. Формат один, каналы два.

### D4. След не становится вторым источником истины

**Решение.** В след попадает только то, что уже есть в событиях контракта или в срезах. Сырой `PlantState` и внутренности движка не пишутся.

**Почему.** Иначе след разъедется с тем, что видит руководитель и что показывает разбор.

### D5. Один эталонный файл на старте

**Решение.** В фикстуры кладётся один след (чистый или с помехой `incoming`). Остальное проверяется инвариантами. Любой прогон можно сохранить в тот же формат.

**Почему.** Агенту достаточно одного живого примера. Полный набор эталонов на все комбинации дорог в поддержке.

### D6. Формат следа

**Решение.** След — один JSON-объект с тремя частями: шапка, события, кадры.

```jsonc
{
  "meta": { "seed": 42, "level": "clean", "overlay": "incoming",
            "horizonShifts": 12, "shiftMinutes": 720 },
  "events": [ /* по возрастанию at */ ],
  "frames": [ /* по одной на границу смены */ ]
}
```

**События.** Шесть типов. У всех общий набор: `at` (минута) и `type`. Поля взяты из примера `docs/TRACE-EXAMPLE.json`, а не придуманы.

| Тип | Поля | Откуда берётся |
|---|---|---|
| `order-registered` | `orderId`, `dueShift` | каталог заказов и `arrivesAt` |
| `batch-appeared` | `batchId`, `orderId`, `qty`, `appearedAt` | `PlantBatch.appearedAt` |
| `operation-ready` | `batchId`, `operationId`, `areaId`, `readyAt` | `PlantOperation.readyAt` |
| `operation-started` | `batchId`, `operationId`, `areaId`, `startedAt` | `ShopStart.at` |
| `operation-completed` | `batchId`, `operationId`, `done`, `good` | `ShopCompletion` |
| `decision-applied` | `decisionType`, `batchId`, `rank`, `appliedAt` | `DecisionRecord` |

Пример одного события:

```json
{ "at": 1920, "type": "operation-started", "batchId": "batch-1",
  "operationId": "batch-1-op-2", "areaId": "area-heat", "startedAt": 1920 }
```

**Почему именно эти шесть.** Пролёживание восстанавливается как `operation-started.startedAt − operation-ready.readyAt`; переход на следующий участок виден по паре «закрытие этой операции → готовность следующей». Других событий для движения не нужно, а лишние увеличивают файл без пользы.

**Про `good` и `done`.** `done` — сколько штук закрыто порцией, `good` — сколько из них годных. При частичном закрытии событий несколько: это не дубли, а порции.

**Кадры.** По одному на границу смены:

```json
{ "shift": 2, "at": 1440,
  "metrics": { "portfolio": { "value": 4, "coverage": 1 } },
  "batches": [ { "batchId": "batch-1", "orderId": "order-1",
                 "areaId": "area-heat", "status": "running",
                 "waitingMinutes": 480 } ] }
```

**Чего в кадре нет.** Полного `PlantState`, плановых штук по операции, `readyAt` и `startedAt` операции. Кадр — точка сверки и быстрой перемотки, а не второй срез цеха.

**Сверка с примером.** `docs/TRACE-EXAMPLE.json` — эталон формы: 9 событий и 2 кадра, все шесть типов представлены. Реализация обязана давать ту же форму; расхождение полей — дефект, а не расширение.

### D7. Объём следа — измерен, а не оценён

**Замер** прогона `clean`/`incoming`, seed 42, горизонт 12 смен:

| Что | Количество |
|---|---|
| Событий всего | **155** |
| из них `operation-ready` | 42 |
| `operation-started` | 36 |
| `operation-closed` | 66 |
| `order-registered` | 5 |
| `batch-created` | 6 |
| `decision-applied` | 0 (решений не принимали) |
| Кадров смен | 12 |
| **Объём следа** | **≈ 22 КБ** |

Расчёт: событие ≈ 106 байт, кадр ≈ 522 байта.

**Почему это важно записать.** След не станет тяжёлым: 22 КБ против 12 КБ текущего отчёта — тот же порядок. Полный файл читается внешним агентом целиком, дробить не нужно. Если однажды горизонт вырастет или появится больше партий, объём растёт линейно, и это видно по этой же таблице.

### D8. Кадры и разбор не дублируют друг друга

**Зачем записано.** `sim-ui-review` запрашивает срез цеха на смену разбора. След тоже содержит кадры. Пока это разные артефакты с разными задачами:

| | Кадр следа | Срез цеха для разбора |
|---|---|---|
| Что | краткое положение партий и показатели | полный `PlantState` на смену |
| Когда нужен | проигрывание и перемотка | сверка записи с фактом |
| Кто читает | внешний агент, будущий UI игры | экран разбора |

**Решение.** Кадр **не заменяет** срез цеха для разбора: в кадре нет ни `done`, ни `readyAt`, без которых вердикт не посчитать. Если позже понадобится один артефакт вместо двух — кадр расширяется до среза, но это отдельное изменение, а не подразумеваемое.

## Risks / Trade-offs

- [След станет большим] → измерено: **22 КБ** на 12 смен при 155 событиях. Растёт линейно от горизонта и числа партий, потолок известен.
- [Формат файла и API разъедутся] → один тип, файл — сериализация того же объекта, что отдаёт API. Проверяется тестом: содержимое файла и ответа совпадает побайтово.
- [Агент захардкодит времена] → в описании для агента явно: времена модельные, структура предметная.
- [Кадр следа примут за срез цеха] → в кадре нет `done` и `readyAt`, вердикт разбора по нему не посчитать. Записано в D8, проверяется тестом: в кадре нет этих полей.
- [Новый маршрут нарушит «контракт не меняется»] → маршрут добавляется, существующие не трогаются. Схема и клиентские типы пересобираются, тест сверки описания с ответами ловит расхождение.

## Open Questions

Закрыты:

1. Частота — события на каждое значимое изменение + кадры смен.
2. Доставка — и файл (для агента и сохранения), и API (для UI). Формат один.
3. Явные стрелки — не нужны.
4. Формат событий и кадров — D6, шесть типов событий с точными полями.
5. Объём — D7, измерен: 22 КБ.
6. Отношение к разбору — D8, кадр не заменяет срез цеха.
