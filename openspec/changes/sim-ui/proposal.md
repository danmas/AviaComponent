## Why

Контракт API готов и проверен: версия `/v1`, описание `openapi.json`, клиентские типы, поток событий, три среза видимости. Дальше нужен экран — но именно здесь лежит риск, названный при подготовке `sim-api-contract` (D9): **интерфейс руководителя сложный, и представлений будет несколько**.

Замеры, определившие это изменение (стенд `clean`/`none`, seed 42, срез на смене 0):

| Факт из контракта | Значение | Что из него следует |
|---|---|---|
| `acceptedShift.coverage` на смене 0 | **0.083** (3 отметки из 36) | Показатель, на который руководитель смотрит первым, в начале почти пуст — это не дефект, а предмет игры |
| `portfolio.coverage`, `overload.coverage`, `scheduleRisk.coverage` | 1.0 | Покрытие у каждого показателя своё, общий процент вводил бы в заблуждение |
| `queueByUnit` | станко-часы, человеко-часы, сутки садки **отдельно** | Очередь нельзя сложить в одно число — обычный дашборд соврёт |
| `scheduleRisk.value.unevaluated` | 0 на `clean` | «Не оценено» — отдельное состояние, а не ноль |
| `overload.value.areas[].problem` | `ok` / `unit-mismatch` / `zero-capacity` | У числа есть причина недоверия, и её надо показать |
| `summary.reliability[]` | по строке на показатель | Реестр достоверности уже в контракте, отдельной формулы не нужно |
| `reads` у каждого показателя | `['orders','norms','facts']` и т.п. | Происхождение числа известно и показывается по запросу |
| `decisionJournal[]` | момент, действие, основание, покрытие, последствие | Цена решения видна до и после, а не только «выполнено» |
| `roles.records[]` | 6 видов записей с `contractDue: null` возможным | Пустое поле — штатное состояние, его нельзя рисовать нулём |

**Главный вывод.** Данные для честного экрана в контракте есть: покрытие у каждого числа, причина недоверия, несложимые единицы, происхождение. UI не должен ничего досчитывать — иначе появится второе место с правилом, и расхождение будет молчаливым.

**Зачем отдельная спека, а не «сразу экран».** `README_Game_v1.md` требует три слоя (цех, рабочие места ролей, свод) плюс разбор. Если начать с вёрстки, первый экран продиктует форму данных и второй клиент по ней не построится — риск, зафиксированный в `sim-api-contract` D9. Поэтому сначала фиксируются решения о представлении, потом код.

## What Changes

- Появляется каталог `SIM/ui/` — React + Vite, отдельное приложение, потребляющее контракт через `api-client`. Первый экран — **цех**: маршрут участков, партии на маршруте, очереди, простои, движение между сменами.
- Визуальный язык: **бланк первичного учёта**, а не аналитический дашборд. Число рисуется пропорционально своему покрытию: плотная тушь при высоком, выцветшее и пунктирное при низком.
- Появляется правило «несложимо»: очередь по разным единицам показывается раздельно и никогда не суммируется на экране.
- Появляется различение состояний «нет данных» (`null`) и «ноль» (`0`) — разными знаками, не цветом.
- Такт игры: один экран = одна смена, не более трёх решений за смену.
- Появляется разбор смены: единственное место, где видно цех.

Не меняется:

- Ядро, контракт `/v1`, `openapi.json`, клиентские типы. UI **потребляет** контракт и не требует его правок.
- Правило видимости: главный экран не показывает цех, цех не показывает записи.
- Расчёт показателей. UI не суммирует, не усредняет и не переводит единицы.
- Формулы, ёмкости, `CONTRACT_STAND`, `EXPECTED`.

## Capabilities

### New Capabilities

- `sim-ui-language`: визуальный язык — бланк, число с весом по покрытию, различение «нет данных» и нуля, несложимые единицы.
- `sim-ui-shop`: экран цеха — маршрут участков, место каждой партии, очередь участка, простой ресурса, движение за период.
- `sim-ui-dashboard`: главный экран руководителя — четыре показателя, реестр достоверности, происхождение числа.
- `sim-ui-decisions`: решения за смену с ценой до подтверждения, ограничение в три действия.
- `sim-ui-review`: разбор смены — сопоставление «что видел руководитель» и «что было в цехе».

### Modified Capabilities

Нет. Контракт не меняется — это и есть проверка его годности.
