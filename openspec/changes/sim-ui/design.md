## Context

См. [proposal.md](proposal.md). Замеры по контракту на смене 0, стенд `clean`/`none`, seed 42:

| Показатель | `coverage` | Значение |
|---|---|---|
| `portfolio` | 1.0 | `openCount`, `remainderNormHours`, `ordersWithoutNorm` |
| `overload` | 1.0 | 6 участков, `queueByUnit` |
| `acceptedShift` | **0.083** | 3 отметки из 36 |
| `scheduleRisk` | 1.0 | `overdue`, `onTime`, `unevaluated` |

Два числа определяют весь язык экрана. Первое — покрытие `acceptedShift` равно 0.083 на первой смене: руководитель видит показатель, собранный на трёх записях из тридцати шести. Второе — `portfolio`, `overload` и `scheduleRisk` имеют покрытие 1.0, то есть **разное покрытие у разных чисел на одном экране — норма, а не сбой**.

Ещё три факта из типов: `OverloadValue.queueByUnit` разделяет станко-часы, человеко-часы и сутки садки (сложить нельзя); `ScenarioRiskValue.unevaluated` — отдельное поле, не ноль; `RoleRow.contractDue` бывает `null` при `status: 'draft'`.

## Goals / Non-Goals

**Goals**

- Число на экране несёт свой вес достоверности: игрок видит, насколько число надёжно, не читая подпись.
- «Нет данных» и «ноль» различимы без цвета.
- Очередь по разным единицам не складывается нигде на экране.
- Цена решения видна до подтверждения, а не после.
- Разбор смены показывает расхождение «видел ↔ было» числами.

**Non-Goals**

- Рабочие места ролей (этап 5) и разбор с вердиктами.
- Остальные семь решений руководителя.
- Аутентификация, мультиплеер, сохранение прогресса.
- Мобильная вёрстка, темы, доступность сверх базовой.
- Копирование живого экрана «Альфа-Пром» пиксель в пиксель.

## Decisions

### D1. Бланк, а не дашборд

**Решение.** Визуальный язык — первичный учётный документ: бланк с полями, штампами, подчёркиваниями. Не карточки с крупными цифрами, не графики, не «плитки».

**Почему.** Экран показывает **записи**, а не физический мир. `sim-data-contract` уже развёл два мира, и экран обязан это выражать: руководитель смотрит на документ, заполненный другими людьми. Дашборд создаёт противоположное впечатление — будто за числом стоит измерение. Домен это подтверждает: маршрутный лист, сопроводительная карта, сменное задание — всё бумажные формы.

**Следствие.** Никаких sparkline, круговых диаграмм и градиентов. График появится только там, где он несёт сравнение, и только на экране цеха.

### D2. Число с весом: покрытие задаёт плотность

**Решение.** Каждое число рисуется с визуальным весом, выведенным из его `coverage`: 90–100% — плотная тушь; 60–89% — обычная; 30–59% — выцветшее, с подчёркиванием пунктиром; ниже 30% — контур вместо заливки.

**Почему.** Замер: на одном экране соседствуют покрытие 1.0 и 0.083. Подпись «покрытие 8%» мелким шрифтом игрок пропустит — а это и есть главная информация. Вес сам по себе читается без чтения.

**Правило.** Перевод покрытия в вес живёт **в одном месте** — `SIM/ui/src/lib/coverage.ts`. Компонент не вычисляет вес сам: иначе два экрана дадут разные пороги.

**Проверка.** Тест на функцию перевода: покрытие 1.0 → полный вес, 0.083 → контур, границы (0.3, 0.6, 0.9) не размыты.

### D3. «Нет данных» — не ноль

**Решение.** `null` рисуется прочерком с подписью «не заполнено»; `0` — нулём. Различие не цветом, а знаком: прочерк, пунктирная рамка, отсутствие заливки.

**Почему.** `contractDue: null` означает «коммерсант не внёс дату», а `0` означало бы «срок наступил сейчас» — противоположные смыслы. Замер: `scheduleRisk.unevaluated` отдельным полем, то есть в контракте это уже разведено; на экране различие обязано сохраниться.

**Запрет.** Никакой подстановки `0`, `—` вместо `null` без подписи, и никакого `?? 0`.

### D4. Несложимые единицы

**Решение.** Очередь показывается по единицам раздельно: `станко-часы`, `человеко-часы`, `сутки садки` — отдельными строками со своей единицей. Итоговой суммы нет ни в одном месте экрана.

**Почему.** Замер: `queueByUnit` в контракте уже сгруппирован по единице, потому что сложение разных единиц бессмысленно. Если UI сложит, он создаст второе место с правилом — а ядро так делать запрещает (`units.ts`: `add` падает на разных единицах).

**Следствие.** «Перегрузка участков» не имеет одного числа. Вместо него — сколько участков перегружено и очередь по каждой единице.

**Проверка.** Тест: при очереди 4 станко-часа и 2 суток садки на экране две строки, суммы 6 нет.

### D5. Цвет — только достоверность

**Решение.** Цветовая шкала одна: достоверность. Красный/зелёный как оценка («плохо/хорошо») не используется.

**Почему.** Оценка — предмет решения игрока, а не свойство числа. Если система красит плохое в красное, игра превращается в «следуй подсказкам» и проверять нечего. Достоверность же — свойство данных, и её показывать честно.

**Следствие.** Плохое решение выглядит как обычное число с хорошей тушью. Это и есть предмет тренажёра: решение принимается при неполных данных.

### D6. Такт: одна смена — один экран решений

**Решение.** Экран не тикает в реальном времени. Один такт = одна смена. Решений за смену не больше трёх; счётчик виден.

**Почему.** Игра про суждение, а не про скорость реакции. Ограничение в три действия — дизайнерское, не техническое: когда выбор ограничен, каждое нажатие весит. `README_Game_v1.md` задаёт 1–3 действия за смену; берём верхнюю границу.

**Следствие.** Никаких таймеров, автообновлений и «живых» счётчиков. Экран меняется только по действию игрока.

### D7. Цена решения — до подтверждения

**Решение.** Перед подтверждением показывается цена: покрытие основания, на котором принимается решение, и что решение не изменит. Не «Вы уверены?», а именно числа:

```
Сменить приоритет: batch-3 → ранг 0
основание: риск сроков, покрытие 100%
━━━━━━━━━━━━━━━━━━━━━━━━━
прошлое не пересчитывается
начатая операция не прерывается
[ отмена ]  [ применить ]
```

**Почему.** Контракт отдаёт `decisionJournal` с `basisMetric`, `basisValue`, `coverage`, `consequence`. Всё уже есть — UI обязан это показать на входе, а не только в журнале после. Иначе решение принимается вслепую, и игра ничему не учит.

**Чего не будет.** «Из 10 похожих обещаний сорвано 7» — такой статистики в контракте нет, и выдумывать её из одного прогона нельзя. Показываем только то, что пришло.

### D8. Разбор смены — единственное место, где виден цех

**Решение.** По завершении смены открывается разбор: слева — что видел руководитель (срез `summary` на эту смену), справа — что было в цехе (срез `shop`). Расхождение показывается парами «запись против факта».

**Почему.** Управленческая асимметрия — главная механика: руководитель видит только записи, правда доступна в разборе. Если цех виден всегда, асимметрии нет и проверять нечего.

**Следствие.** Срез `shop` запрашивается **только** при открытии разбора — отдельным сетевым вызовом. Это не оптимизация, а правило видимости: клиент руководителя не должен держать цех в памяти во время принятия решения.

### D9. Каталог `SIM/ui/`, порт 5173

**Решение.** Отдельное приложение в `SIM/ui/` со своим `package.json`. Vite, порт 5173. Потребляет контракт только через `api-client`.

**Почему.** Клиент уже проверен тестом на независимость от сервера. UI обязан использовать его, а не писать свой транспорт: иначе версия `/v1` и проверка `apiVersion` останутся в стороне. Замер: порт 5173 свободен.

**Запрет.** UI не импортирует `SIM/plant/`, `SIM/system/`, `SIM/contract/` и `SIM/api/` — ни для типов, ни для расчётов. Проверяется границей.

### D10. Проверка языка до объёма

**Решение.** Первый вертикальный срез — **один** экран (главный, с четырьмя показателями и реестром) на одном уровне сложности и одной смене. Рабочие места ролей и остальные решения — после того, как язык проверен на этом срезе.

**Почему.** Риск «хороший интерфейс так просто не построится» проверяется дешевле всего на одном экране. Если язык не работает на четырёх показателях, он не заработает и на восьми решениях.

**Следствие.** В этом изменении три слоя экранов **не** реализуются. Реализуется свод и разбор; цех как отдельный экран и рабочие места ролей — следующие изменения.

## Risks / Trade-offs

- [Вес по покрытию может читаться как «сломано», а не как «ненадёжно»] → функция веса проверяется тестом на границах, а на экране есть легенда один раз за сессию. Если на живом экране непонятно — правится порог, а не механика.
- [Отказ от красного/зелёного сделает экран скучным] → скучный экран здесь цель: оценка принадлежит игроку. Проверяется на разборе — там расхождения видны без цвета.
- [Три решения за смену может оказаться мало при восьми типах] → в этом изменении один тип решения, три — с запасом. Граница пересматривается, когда появятся остальные.
- [Дорого: React + Vite в отдельном каталоге] → это цена нескольких клиентов, ради которой затевался `sim-api-contract`. Альтернатива — один самописный экран на ванильном JS — сломается на втором экране.
- [Срез цеха в разборе тяжелее свода в 8 раз (12 КБ против 1.5 КБ)] → запрашивается только при открытии разбора, не кешируется между сменами.

## Migration Plan

Новый каталог, миграции нет. Откат — удалить `SIM/ui/` и зависимость. Контракт, ядро и тесты не меняются: если после удаления `SIM/ui/` `npm test` в `SIM/` зелёный, откат полный.

## Open Questions

**Закрыты замерами:** язык (D1–D5), такт (D6), показ цены (D7), видимость цеха (D8), расположение (D9), объём первого среза (D10).

**Открыт один.** Как именно рисовать «вес» технически: прозрачность текста, толщина линии или плотность заливки. Решается при реализации по критерию — вес должен читаться при **самом мелком** кегле на экране и при чёрно-белой печати. Если прозрачность при мелком кегле не читается, берётся толщина подчёркивания.
