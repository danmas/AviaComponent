### Доменная единица времени

Операции измеряются в часах и днях. Смена — 12 ч, две смены в сутки. Горизонт первой версии — 10–15 смен. Секундная точность не нужна: дискретно-событийная симуляция с шагом по событиям достаточна.

### Границы

Первоисточники не изменяются. Живая система недоступна: контракт проектируется по документам, а не по её коду.

## Goals

- Формально разделить два мира так, чтобы Система **физически не могла** прочитать скрытое состояние цеха.
- Описать деградацию данных на границе: задержка, дубликат, пропуск, искажение.
- Дать формулы четырёх показателей, привязанные к записям, а не к истине.
- Зафиксировать формат журнала решений как источника требований к ТЗ.

## Non-Goals

- Полная копия схемы 103 таблиц живой системы. Модель — не реплика БД.
- Промышленная нагрузка, SLA, восстановление после отказа.
- Телеметрия станков (FOCAS2 / OPC UA) — пилот сверх договорного ТЗ.
- Прослеживаемость 9100 / 9102, Nadcap — вне исходного договора.
- UI и визуализация — этап 2.

## Decisions

### D1. Два мира разделены типами, а не соглашением

**Решение.** Сущности мира предприятия и мира Системы — разные типы в разных модулях. Обмен только через типизированные события контракта.

**Обоснование.** Если оба мира импортируют один тип `Part` и читают общее поле, асимметрия исчезнет при первом же удобном случае: кто-то возьмёт «настоящую» дату напрямую. Типы не дают этого сделать.

**Следствие.** Модуль Системы не импортирует модуль предприятия. Проверяется линтером правил импорта.

### D2. Детерминизм через seeded RNG, состояние — один корень

**Решение.** Один seed на прогон. Всё случайное — через один генератор, передаваемый явно. Состояние симуляции сериализуется целиком.

**Обоснование.** Иначе эксперимент не воспроизвести, а сравнивать сценарии между собой будет нельзя. Скрытый `Math.random()` — самая частая причина невоспроизводимых прогонов.

**Следствие.** Глобального `Math.random()` в коде модели нет. Прогон с тем же seed даёт побайтово тот же отчёт.

### D3. Задержка отметки — параметр дисциплины, а не свойство события

**Решение.** Событие факта несёт **истинное время** (когда произошло) и **время записи** (когда попало в Систему). Оба обязательны.

**Обоснование.** Противоречие 03 и зона Б3 — про то, что факт приходит с опозданием. Если хранить только одно время, разрыв не измерить. Два поля дают метрику запаздывания бесплатно.

**Следствие.** Показатель «принято за смену» считается по времени записи, а факт исполнения — по истинному. Их расхождение и есть измеряемая деградация.

### D4. Пропуск отметки — отсутствие события, а не событие с флагом

**Решение.** Если мастер не отметил, события нет вовсе. Дыра в данных — это отсутствие записи, не `flag: missed`.

**Обоснование.** В живой системе именно так: нет строки — нет факта. Флаг «пропущено» был бы подсказкой, которой у руководителя в реальности нет.

**Следствие.** Покрытие показателя считается как доля ожидаемых записей, которые физически есть. Модель знает, сколько должно быть; Система — нет.

### D5. План хранится версиями, хотя ТЗ этого не требует

**Решение.** Каждый расчёт плана создаёт неизменяемую версию с отметкой времени и причиной пересчёта. Снимок утверждения смены — отдельная сущность.

**Обоснование.** ТЗ не требует хранить план, и именно поэтому в живой системе `shift_task_snapshots` = 0. В модели это **сознательное отклонение**: без версии нельзя сравнить обещанный срок с фактом, а это и есть предмет игры. Отклонение фиксируется как требование к доработке Системы.

**Следствие.** Журнал решений может показать: «план пересчитан N раз за смену, вот причины».

### D6. Четыре показателя считаются по записям, доступным Системе

**Решение.** Формулы показателей используют только записи, которые есть в Системе. Истина мира предприятия в расчёт не входит ни на одном шаге.

**Обоснование.** Это граница смысла игры. Показатель, посчитанный по истине, — уже не показатель Системы, а отчёт модели.

**Следствие.** Каждая формула сопровождается перечнем используемых записей. Проверяется тестом: подмена скрытого состояния не меняет значение показателя.

### D7. Журнал решений — событийный лог, не оценка

**Решение.** Журнал пишет действие, момент, показатель-основание, его покрытие и последствие. Очков и рейтингов нет.

**Обоснование.** Цель — извлечь требования к ТЗ, а не оценить игрока. Оценка («плохое решение») требует нормы, которой у нас нет; факт («обещал срок при покрытии 28%, сорвал») — не требует.

**Следствие.** Разбор партии читается как протокол, а не как экран результатов.

### D8. Единицы измерения — отдельный тип, не число

**Решение.** н/ч, станко-часы, человеко-часы, печь-часы, сутки садки — разные типы. Сложение разнородных единиц — ошибка компиляции, а не рантайма.

**Обоснование.** Смешение единиц зафиксировано в документах как риск. Типы делают его невозможным в коде модели — и заодно демонстрируют заказчику, как это должно быть устроено.

**Следствие.** Перевод — только явной функцией с указанием основания перевода.

### D9. Контракт версионируется, старые события не переписываются

**Решение.** Контракт несёт версию. Событие, записанное ранее, читается по своей версии.

**Обоснование.** Этапы 3 и 4 будут менять состав событий. Без версии прогоны этапа 1 станут нечитаемыми.

**Следствие.** Схемы событий — в `SIM/contract/vN/`.

### D10. Три слоя видимости, а не два

**Решение.** Контракт обслуживает три уровня экранов: цех (реальность), рабочие места ролей (записи), главный экран руководителя (свод). Каждый уровень читает свой срез данных и не имеет доступа к соседнему.

**Обоснование.** Основная идея игры — проверить, как модель Системы работает на модели Предприятия. Для этого нужно видеть **оба** мира одновременно и видеть **шов** между ними. Если цех только «за кадром», проверить нечего: расхождение нельзя показать.

Отсюда три следствия для контракта:

1. Состояние цеха должно быть полностью наблюдаемым — экран цеха читает его напрямую, минуя Систему.
2. Каждая роль вносит свою часть записей — контракт описывает не один поток «отметок», а девять потоков ввода по ролям.
3. Свод собирается только из записей — но именно поэтому сравнение с цехом даёт результат.

**Следствие.** Схема данных включает наблюдаемое состояние цеха (участки, станки, партии, простои) как отдельный срез, доступный только экрану цеха и разбору.

## Risks

| Риск | Оценка | Смягчение |
|------|--------|-----------|
| **Асимметрия протечёт** — модель Системы получит доступ к истине | высокая | разные типы (D1) + правило линтера на импорты + тест «подмена скрытого состояния не меняет показатель» (D6) |
| **Контракт окажется слишком богатым** — в него протекут поля, которых в реальной Системе нет | средняя | каждое поле обосновывается документом; поля без опоры помечаются как гипотеза |
| **Модель подгонят под Систему** — числа подберут так, чтобы всё сходилось | средняя | параметры фиксируются до прогона в `tasks.md`; после прогона не двигаются |
| **Схема данных станет мини-копией БД на 103 таблицы** | низкая | Non-Goals: модель — минимальный набор для четырёх показателей |
| **Единицы всё равно смешаются на уровне отчётов** | средняя | D8 + тест на попытку сложения |

### Честный прогноз

Этап даёт **бумажный артефакт**: типы, схемы, формулы, тесты формы. Никакой визуализации и никаких выводов о живой системе.

Ценность этапа — в двух вещах: (1) контракт, которого у заказчика нет; (2) невозможность случайно сделать Систему всеведущей. Если после этапа окажется, что четыре показателя не собираются из записей без истины — это будет важный и неприятный результат: значит, часть показателей в принципе недоказуема, и это нужно сказать, а не обойти.
