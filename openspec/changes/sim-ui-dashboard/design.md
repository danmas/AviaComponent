## Context

См. [proposal.md](proposal.md). Язык экрана уже задан в `sim-ui` (D1–D5): бланк первичного учёта, число с весом по покрытию, «нет данных» ≠ ноль, несложимые единицы, цвет только для достоверности. Этот экран строится на том же языке, не вводя второго.

Проверено на смене 4 (`overlay: incoming`, seed 42): `portfolio.coverage = 0.8`, `acceptedShift.coverage = 0.111`, `overload` и `scheduleRisk` — 1.0. Решение отдаёт `basisMetric`, `basisValue`, `coverage`, `consequence`.

## Goals / Non-Goals

**Goals**

- Покрытие видно на экране, включая падение при неразобранном заказе.
- Цена решения видна **до** подтверждения, а не после.
- Журнал решений читается: что, на каком основании, с каким покрытием.
- Экран не считает показатели: только раскладывает пришедшее.
- Переключение между цехом и сводом без потери сессии.

**Non-Goals**

- Разбор смены и сопоставление «видел ↔ было».
- Новые показатели.
- Рабочие места ролей.
- Изменение контракта: свод собирается из существующих ответов.

## Decisions

### D1. Покрытие — главный элемент экрана, а не подпись

**Решение.** Каждое число показателя рисуется с весом по покрытию (как задано в `sim-ui` D2), а рядом — покрытие и число записей, из которых показатель собран. Реестр достоверности идёт **первым блоком**, до значений.

**Почему реестр первым.** Замер: на одной смене соседствуют покрытия 1.0, 0.8 и 0.111. Если реестр внизу, игрок читает значения раньше, чем узнаёт, насколько им верить. Порядок чтения задаёт доверие.

**Следствие.** Один и тот же порог перевода покрытия в вес — из `coverage.ts`, второй не вводится.

### D2. Падение покрытия показывается изменением, а не только числом

**Решение.** Если покрытие показателя упало с прошлого среза, рядом с ним ставится знак падения с указанием, на сколько и из-за чего: «покрытие 0.8 (было 1.0, −0.2: неразобранный заказ order-5)».

**Почему.** Замер: приход неразобранного заказа снижает `portfolio` с 1 до 0.8. Само по себе 0.8 — просто число; игрок не знает, было ли так всегда. Изменение сообщает, что **что-то произошло**, и это единственный сигнал «надо решать».

**Ограничение.** Причина называется только из того, что известно клиенту: список неразобранных заказов есть в срезе ролей. Если причина не выводится из данных, пишется «покрытие снизилось» без объяснения — но не выдумывается.

### D3. Цена решения — из журнала, а не из расчёта на клиенте

**Решение.** Перед подтверждением показывается блок: показатель-основание, его значение, покрытие и текст последствия. Все четыре берутся из ответа сервера (`basisMetric`, `basisValue`, `coverage`, `consequence`), клиент их не сочиняет.

**Почему.** Проверено: сервер уже отдаёт всё четыре. Если клиент начнёт считать последствие сам, появится второе место с правилом модели — тот же запрет, что в `sim-api` D3a.

**Как это выглядит.** До нажатия «применить»:

```
Приоритет партии batch-7: ранг 0
основание: риск сроков — просрочено 1, в срок 4, без оценки 0
покрытие основания: 1.00
──────────────────────────
ранг действует с начала этой смены;
уже выданный срез не пересчитывается
[ отмена ]  [ применить ]
```

**Чего не будет.** «Из 10 похожих решений сорвано 7» — такой статистики в контракте нет. Показывается только то, что пришло.

### D4. Три решения за смену, счётчик виден

**Решение.** За смену принимается не больше трёх решений. Счётчик «решено 2 из 3» виден постоянно, четвёртое действие недоступно с объяснением.

**Почему.** Действия в тренажёре: приоритет, принять заказ, отложить заказ — три типа. Ограничение не техническое, а игровое: когда выбор ограничен, каждое нажатие весит. `README_Game_v1.md` задаёт 1–3 действия за смену, берётся верхняя граница.

**Где считается.** Счётчик — по `decisionJournal` текущей смены: решения с `at` в пределах смены. Клиент не заводит своего счётчика, чтобы он не разошёлся с журналом.

### D5. Журнал — список фактов, без оценки

**Решение.** Журнал показывает записи по порядку: момент, действие, показатель-основание, покрытие, последствие. Никакого балла, никакого «хорошо/плохо».

**Почему.** Оценка — предмет разбора (следующее изменение), а не журнала. Журнал фиксирует, что было решено и на чём, чтобы разбор мог это сопоставить с фактом. Если журнал начнёт оценивать, разбор потеряет опору.

**Запрет.** Никаких рейтингов, баллов, процентов успеха, цветовой оценки решений. Это прямо запрещено в `sim-ui` D5 и подтверждается здесь.

### D6. Два экрана, одна сессия

**Решение.** Цех и свод — два вида одного приложения. Переключение — закладками в шапке. Сессия, смена и состояние решений общие: переключение не сбрасывает прогон и не создаёт новую сессию.

**Почему.** Два экрана показывают **разные миры** одной смены: цех — физику, свод — записи. Игрок должен переключаться свободно, чтобы сопоставлять: увидел очередь на печи в цехе, посмотрел пролёживание в своде. Если переключение сбрасывает сессию, сопоставление невозможно.

**Следствие.** Клиент один, состояние одно. Экран цеха не переписывается — он становится одной из закладок.

## Risks / Trade-offs

- [Падение покрытия можно объяснить неверно] → причина берётся только из данных среза; если вывести нельзя, пишется «покрытие снизилось» без причины. Проверяется тестом: при двух неразобранных заказах причина называет оба, а не первый.
- [Цена решения показывается до подтверждения, но текст последствия приходит с сервера уже после] → проверено: `consequence` есть в ответе на решение. Если его нет до подтверждения, кнопка показывает «последствие: см. журнал» — но не выдуманный текст.
- [Три решения за смену может оказаться мало] → в этом изменении три типа решений, ограничение совпадает с числом типов. Пересматривается при появлении четвёртого типа.
- [Свод дублирует экран цеха по части данных] → намеренно: пролёживание видно в обоих, но в цехе — по участкам, в своде — как показатель. Дубль данных, не дубль правила.
- [Реестр первым блоком может выглядеть как «нет данных» на первой смене] → на смене 0 `acceptedShift.coverage = 0.083`, и это честный сигнал: записей ещё мало. Не ошибка экрана.

## Migration Plan

Новый экран, миграции нет. Экран цеха остаётся, добавляется закладка. Откат — убрать закладку свода; контракт и модель не затронуты.

## Open Questions

**Закрыты:** порядок блоков (D1), показ падения (D2), источник цены (D3), счётчик решений (D4), журнал без оценки (D5), два экрана в одной сессии (D6).

**Открыт один.** Показывать ли на своде **все четыре** показателя или только те, у которых покрытие ниже единицы. Аргумент за «только проблемные»: экран читается быстрее, внимание не рассеивается. Аргумент против: отсутствие показателя игрок прочитает как «его нет», а не «с ним всё в порядке».

Решение при реализации по критерию: если скрытый показатель можно принять за отсутствующий при чтении с листа — показывать все, приглушая полные. Скорее всего так и выйдет: лучше все, но с явным «покрытие 1.00».
