# Изменение: экран свода руководителя

**Этап:** 4.6. Зависит от `sim-ui` (язык), `sim-incoming-orders` (покрытие), `sim-waiting-time` (пролёживание).
**Спецификация игры:** [SIM/README_Game_v1.md](../../../SIM/README_Game_v1.md)

## Зачем это изменение

Три последних изменения работают в модели, но **не видны руководителю**:

| Что введено | Видно на экране сейчас |
|---|---|
| Пролёживание | только на экране цеха, по участкам |
| Падение покрытия при неразобранном заказе | **нет** — только «есть неразобранный заказ» |
| Цена решения (`basisMetric`, `coverage`, `consequence`) | **нет нигде** |

Экран цеха показывает физику. Руководитель решает по **записям** — и записей он не видит. Свод закрывает это.

## Замер, из которого всё следует

Смена 4, `overlay: incoming`, seed 42:

| Показатель | Покрытие | Значение |
|---|---|---|
| `portfolio` | **0.8** | 5 заказов в портфеле |
| `overload` | 1 | 6 участков |
| `acceptedShift` | **0.111** | 4 отметки из 36 |
| `scheduleRisk` | 1 | просрочено 1, в срок 4 |

Покрытие `portfolio` упало с 1 до 0.8 — потому что пришёл неразобранный `order-5`. **Сейчас этот сигнал виден только в отчёте прогона, а не игроку.**

## Ключевая мысль экрана

**Реестр достоверности — первым блоком, до значений.** На одной смене соседствуют покрытия 1.0, 0.8 и 0.111. Если реестр внизу, игрок прочитает значения раньше, чем узнает, насколько им верить. Порядок чтения задаёт доверие.

## Что уже есть в контракте

**Ничего нового не требуется.** Проверено на живом сервере:

- срез свода: 4 показателя с `coverage`, `reads` и `value`; `reliability[]`; `areas[]` с `capacity`, `plan`, `queue`
- решение отдаёт `basisMetric`, `basisValue`, `coverage`, `consequence`
- срез ролей отдаёт заказы со `status: unparsed` и `contractDue`

Свод собирается из того, что уже приходит. Контракт, схема и типы не меняются.

## Решения

- **D1** покрытие — главный элемент, реестр первым блоком
- **D2** падение покрытия показывается изменением («было 1.0, −0.2: неразобранный order-5»), причина только из данных
- **D3** цена решения — из журнала сервера, не расчёт клиента
- **D4** три решения за смену, счётчик по `decisionJournal`, не свой
- **D5** журнал — факты без баллов и оценки
- **D6** два экрана в одной сессии, переключение не сбрасывает прогон

## Что не входит

- Разбор смены «видел ↔ было» — отдельное изменение.
- Рабочие места ролей.
- Новые показатели: четыре существующих.
- Изменение контракта.

## Открытый вопрос

Показывать все четыре показателя или только те, у которых покрытие ниже единицы. Критерий: если скрытый показатель читается как «его нет», а не «с ним всё хорошо» — показывать все. Скорее всего так и выйдет: все, но полные приглушены и с явным «покрытие 1.00».
