# Изменение: экран разбора смены

**Этап:** 4.7 — последний слой `sim-ui`. Зависит от `sim-ui-dashboard`.
**Спецификация игры:** [SIM/README_Game_v1.md](../../../SIM/README_Game_v1.md)

## Зачем

Свод даёт записи и цену решения. **Проверить, был ли руководитель прав, негде.** Журнал фиксирует основание; факт того, что вышло, нигде не сопоставляется.

Разбор — единственное место, где игрок видит **цех**. Экран свода показывает записи, разбор — что было на самом деле. Без него тренажёр не замыкается.

Это главная механика, ради которой всё делалось: **управленческая асимметрия**. Решаешь по записям, правда — только в разборе. Видно всегда — проверять нечего; не видно никогда — учиться не на чем.

## Что уже есть — без нового контракта

Проверено на живом сервере:

| Что нужно | Где | Состояние |
|---|---|---|
| Записи решений | `decisionJournal` | `at`, `action`, `basisMetric`, `basisValue`, `coverage`, `consequence` |
| Три вердикта | `system/journal.ts` | тип и `review()` **есть, в прогоне не вызывается** |
| Прошлый срез свода | `?shift=N` | 200, `portfolio` 1 → 0.8 восстановимо |
| Прошлый срез цеха | `/shop?shift=N` | 200, 42 операции |
| Сроки | срез ролей | `contractDue` у заказа |
| Факт по партии | срез цеха | `status`, `readyAt`, `startedAt`, `done` |

## Три вердикта — правило, а не мнение

| Вердикт | Когда |
|---|---|
| подтвердилось | следствие наступило так, как записано |
| разошлось | факт отличается от записанного последствия |
| невозможно проверить | данных для сверки нет: нет закрытия или срока |

**Приоритет сверяется по неизменности прошлого, а не по выгоде.** Проверить «помог ли ранг» нельзя: нужно знать, как было бы без него, а второго прогона в игре нет. Записанное последствие («прошлый срез не пересчитывается») проверяемо — прошлый срез действительно не изменился. Вердикт идёт по этому.

Это важнейшее решение этапа: без него реализация попытается сравнить «с рангом» и «без ранга» и выдаст выдуманный вердикт.

## Где считается вердикт

**На клиенте**, в `SIM/ui/src/lib/review.ts`. Ядро и контракт не меняются.

Почему не в ядре: ядро не знает про решения как про объект — их хранит API-сессия. Протащить журнал внутрь прогона значит изменить прогон ради UI. Вердикт — сравнение двух уже посчитанных фактов, он не воспроизводит ни одного правила цеха.

## Ключевое ограничение

**Разбор не оценивает поступок.** «Подтвердилось» — не похвала, «разошлось» — не наказание. Баллов, рейтингов, процентов успеха, зелёного и красного нет. Если добавить оценку, игрок начнёт оптимизировать оценку вместо чтения записей.

## Что входит

- Третья закладка «разбор» в той же сессии.
- Правило вердикта по трём исходам.
- Сопоставление «срок против факта» по каждому заказу.
- Запрос среза цеха только на смену разбора, с явной пометкой «это факт».

## Открытый вопрос

Показывать разбор только по сменам с решениями или по всем. Критерий: если пустая смена всё равно даёт сопоставление «срок против факта» — показывать все. Скорее всего так и выйдет: раздел сроков от журнала не зависит.
