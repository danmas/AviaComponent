## Context

См. [proposal.md](proposal.md). Замеры этого этапа (стенд `clean`/`none`, seed 42, Node v24.13.0, npm 11.6.2):

| Замер | Значение |
|-------|----------|
| Полный прогон 12 смен | 0.7–1.2 мс |
| 12 перепрогонов (смены 0…11) | 25.9 мс |
| Срез свода на смену | 1.42–1.47 КБ |
| `PlantState` (срез цеха) | 11.9–12.1 КБ |
| `SystemRecords` | 15.7 КБ |
| Полный отчёт (`reportJson`) | 10.3 КБ |
| Экспортируемых типов в `contract/` | 39 |
| Экспортируемых типов в `system/` | 23 |
| Порт 3400 | свободен |
| Порт 5173 | свободен |
| `enum` в strip-only режиме | **не поддерживается** (`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`) |

Три цифры определяют решения ниже. Срез свода — 1.5 КБ, срез цеха — 12 КБ: это в 8 раз дороже, и именно поэтому срез цеха отдаётся отдельным маршрутом (D3). Прогон стоит 1 мс, 12 перепрогонов — 26 мс: перепрогон дешевле любой схемы кеширования (D6). `enum` не работает в strip-only — серверный код обязан обходиться `as const` и union-типами, как это уже сделано в ядре (D8).

## Goals / Non-Goals

**Goals**

- Клиент на любом языке выводит типы из одного файла, а не из прозы.
- Изменение формы ответа не ломает уже написанный клиент молча.
- WebSocket-протокол описан полностью: набор событий, неизвестный тип, потеря соединения.
- Проверка «описание совпадает с сервером» автоматическая, а не на глаз.

**Non-Goals**

- React-экраны, вёрстка, состояние UI — этап 4 (`sim-ui`).
- Аутентификация, авторизация по ролям, мультиплеер.
- Сохранение сессий в БД.
- Публикация клиентского пакета в npm — пакет живёт в репозитории.
- Восемь остальных решений руководителя (`sim-priority-decision` 3c).

## Decisions

### D1. Версия в пути, а не в заголовке

**Решение.** Маршруты получают префикс `/v1/`: `POST /v1/sessions`, `GET /v1/sessions/:id`, `GET /v1/sessions/:id/shop`, `POST /v1/sessions/:id/decisions`, `GET /v1/sessions/:id/stream`. Неизвестная версия — `404` с телом `{ error: 'unknown-api-version', supported: ['v1'] }`.

**Почему путь, а не заголовок.** Заголовок версии (`Accept: application/vnd.sim.v1+json`) требует, чтобы каждый клиент его выставлял; забытый заголовок даёт молчаливую работу против «последней» версии, то есть ровно ту проблему, которую версия должна решать. Версия в пути видна в логах, в curl, в браузерной строке и в `openapi.json` без дополнительных соглашений.

**Почему `404`, а не `400`.** Запрос на `/v2/sessions` не некорректен — он адресован другой версии, которой нет. `404` отличает «версия не существует» от «тело запроса плохое», и клиент по коду ответа понимает, что делать.

### D2. Версия есть в теле каждого ответа

**Решение.** Каждый ответ несёт поле `apiVersion: 'v1'` на верхнем уровне. Схема: `{ apiVersion, ...данные }`.

**Почему дублировать путь.** Ответ может быть сохранён в файл, передан в очередь, скопирован в лог. Путь там уже потерян, поле — нет. Стоимость — 18 байт на ответ при 1.5 КБ среза (1.2%), и это дешевле, чем разбор «а от какой версии этот дамп».

### D3. Срез цеха отдельным маршрутом — по замеру, а не по вкусу

**Решение.** `GET /v1/sessions/:id` отдаёт свод (1.5 КБ). `GET /v1/sessions/:id/shop` отдаёт цех (12 КБ). Ни один ответ свода не содержит `operations`, `downtimes`, `resources`, `batches`.

**Почему.** Замер: цех в 8 раз тяжелее свода. Если отдавать оба в одном ответе, каждый запрос свода (а их на смену несколько) тянет 12 КБ, которые руководителю не нужны. Это не только трафик: `sim-api` D4 уже требует, чтобы срез цеха не попадал в ответ без явного запроса, — асимметрия «руководитель не видит цех» должна быть выражена и в транспорте, не только в типе.

**Проверка.** Тест: в теле `GET /v1/sessions/:id` нет ключей `operations`, `downtimes`, `resources`, `batches`; в теле `GET /v1/sessions/:id/shop` есть `layer: 'shop'`.

### D4. OpenAPI генерируется из типов, а не пишется руками

**Решение.** `openapi.json` собирается скриптом `npm run openapi` из JSON Schema, выведенных из типов `contract/` и `system/`. Ручная правка `openapi.json` запрещена — файл помечен как сгенерированный, в шапке `x-generated: true` и команда сборки.

**Почему.** Замер: 39 типов в `contract/` и 23 в `system/`. Руками их описание разойдётся с кодом на первом же изменении — это не гипотеза, а свойство любого второго источника истины рядом с типом (тот же аргумент, что в `sim-api` D2 против хранения `PlantState` в сессии).

**Цена.** Нужен генератор JSON Schema из TypeScript. Варианты: `typescript-json-schema` (по типам, без запуска кода), `ts-json-schema-generator`, ручные схемы Fastify. Выбор — за реализацией; требование одно: **изменение типа в ядре обязано менять `openapi.json`**, и это проверяется тестом.

**Проверка.** Тест сравнивает схемы ответов в `openapi.json` с фактическими ответами сервера на фиксированном прогоне. Расхождение — падение.

### D5. Клиентский пакет с типами, сгенерированными из OpenAPI

**Решение.** `SIM/api-client/` содержит: типы (из `openapi.json`), тонкую обёртку `createClient(baseUrl)`, и не содержит ни одной строки, написанной под конкретный экран.

**Почему отдельный пакет, а не папка внутри `SIM/api/`.** Клиент не должен тянуть серверные зависимости. Отдельный каталог со своим `package.json` и `tsconfig.json` делает это проверяемым: если клиент импортирует `fastify`, установка падает.

**Правило.** Клиент не знает про React, про DOM и про `fetch` конкретной среды: транспорт передаётся снаружи (`fetch` по умолчанию), чтобы тот же клиент работал в Node для прогонов в тестах.

### D6. Кеша нет, и это решение, а не пропуск

**Решение.** Каждый запрос среза пересчитывает прогон с горизонтом `currentShift + 1`. Кеш не вводится.

**Почему.** Замер: 12 перепрогонов подряд — 25.9 мс, то есть один перепрогон ≈ 2 мс. Запрос среза делает один перепрогон. Сеть до `localhost` стоит больше, чем прогон. Кеш добавил бы ключ `(seed, level, overlay, decisions до N)`, инвалидацию при каждом решении и риск отдать устаревший срез — за экономию, которую нельзя измерить на фоне 2 мс.

**Когда пересмотреть.** Если горизонт вырастет до сотен смен: прогон 120 смен стоит 14.7 мс, и при 500 сменах квадратичная цена станет заметной. Тогда — кеш по ключу, но с замером, а не заранее.

### D7. CORS явным списком

**Решение.** Источники читаются из `SIM_API_ORIGINS` (список через запятую). Пустое значение — CORS выключен, разрешены только запросы без `Origin` (curl, тесты, сервер-сервер). `*` в конфигурации отвергается при старте.

**Почему не `*`.** С версии `/v1/` контракт предназначен наружу, и `*` с `credentials` — известная ошибка. Явный список заставляет назвать клиента при настройке. Порт 5173 (Vite) свободен — замер, поэтому первым в списке идёт он.

### D8. Серверный код без `enum` и без декораторов

**Решение.** В `SIM/api/` запрещены `enum`, `namespace`, параметр-декораторы. Только `interface`, `type`, `as const`, union-типы.

**Почему.** Замер: `node e.ts` с `enum` падает — `SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode`. Ядро уже живёт по этому правилу (`ROLES`, `UNIT_KINDS`, `LEVEL_NAMES` — все `as const`). Сервер обязан жить так же, иначе `npm run api` потребует сборки, и появится второй способ запуска.

**Проверка.** Правило добавляется в `boundary.ts`: `enum` в зоне `api` — нарушение. Тест на файл с `enum` в `api/` падает.

### D9. React — отдельный этап, и вот почему

**Решение.** В это изменение React, Vite, вёрстка и состояние UI не входят. Они в `sim-ui`.

**Почему.** Два аргумента.

Первый — порядок зависимости. Контракт, написанный под первый экран, наследует его форму: если первый экран рисует карту потоков, в ответ попадут координаты; если первый экран — таблицу, в ответ попадут колонки. Второй клиент по такой форме не построится. `README_Game_v1.md` требует **три** слоя (цех, рабочие места ролей, свод) плюс разбор — это не один экран, и угадать общую форму по первому нельзя.

Второй — проверяемость. Контракт проверяется тестом (`openapi.json` против ответа), UI проверяется глазами. Смешивать в одном этапе то, что проверяется автоматически, с тем, что проверяется вручную, значит не иметь гейта ни там, ни там.

**Что это значит практически.** Клиентские типы из D5 — это и есть «доказательство годности для UI»: если экран нельзя написать против сгенерированных типов, контракт плох, и это видно **до** того, как написана вёрстка.

### D10. Реестр событий WebSocket закрыт и версионирован вместе с API

**Решение.** Пять типов событий, полный список: `shift-started`, `shift-completed`, `metrics-updated`, `decision-applied`, `session-finished`. Неизвестный `type` на клиенте — не ошибка: клиент обязан его игнорировать (forward compatibility). Журнал событий ограничен последними 200 записями сессии; запрос `lastSeq` старше окна даёт `{ error: 'journal-window-exceeded', oldestSeq }`.

**Почему закрытый список, а не произвольный.** Открытый список означает, что клиент не может исчерпывающе обработать поток. Закрытый список + правило «неизвестное игнорируй» даёт обе вещи: клиент знает, что обязан понимать, и не падает на новом типе от сервера новее его.

**Почему окно 200.** Замер: 12 смен по ~4 события — 48 записей. 200 — четырёхкратный запас на горизонт 15 при будущих решениях. Бесконечный журнал — утечка, которую заметят поздно.

## Risks / Trade-offs

- [Генератор JSON Schema из TS может не покрыть все 62 типа] → проверка D4 ловит расхождение: если тип не попал в описание, тест падает. Первым шагом генератор покрывает только типы, реально попадающие в ответы; остальные — по мере появления маршрутов.
- [Версия в пути ломает маршруты `sim-api`] → да, и это ожидаемо: `sim-api` не реализован (1/13), ломать нечего. Если бы сервер уже работал, потребовался бы переходный период с обоими путями.
- [Клиентский пакет расходится с сервером] → типы генерируются, руками не пишутся; расхождение возможно только при пропущенном `npm run api-client`, и это ловится тестом сборки клиента.
- [CORS-список придётся править при каждом новом клиенте] → так и задумано: новый клиент — осознанное действие, а не молчаливая дыра.
- [Окно журнала 200 может оказаться мало при 15 сменах и восьми решениях] → 15 × (4 + 8) = 180, всё ещё внутри. При выходе за окно клиент получает `oldestSeq` и перечитывает срез с нуля — восстановление есть, потери нет.

## Migration Plan

`sim-api` не реализован, поэтому миграции нет: маршруты сразу получают `/v1/`. Откат — удалить `SIM/api/openapi.json`, `SIM/api-client/`, вернуть маршруты без префикса (если `sim-api` к тому моменту реализован).

## Open Questions

**Открыт один.** Выбор генератора JSON Schema из TypeScript: `typescript-json-schema`, `ts-json-schema-generator` или ручные схемы Fastify с проверкой соответствия типам. Решение принимается при реализации по критерию: генератор обязан видеть `as const` union-типы (`ROLES`, `UNIT_KINDS`, `LEVEL_NAMES`) без запуска кода. Если ни один не справляется — схемы Fastify пишутся руками, но проверка D4 остаётся обязательной.

**Закрыты замерами:** версия в пути (D1) и теле (D2), разделение срезов (D3), отказ от кеша (D6), запрет `enum` (D8), окно журнала (D10).
