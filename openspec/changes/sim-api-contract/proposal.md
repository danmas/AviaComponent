## Why

В `sim-api` уже принято, что клиентов будет несколько и что ядро не знает про транспорт. Но там зафиксирован **один** клиент — React-экран руководителя, и контракт описан в объёме «сервер отдаёт срез». Для нескольких клиентов этого мало, и это не абстрактная тревога, а три конкретных пробела.

**Пробел 1. Нет версии API.** В ядре версионирование уже решено и работает: `contract/version.ts` держит `CONTRACT_VERSION = 1` для записи и `READABLE_VERSIONS = [1, 2]` для чтения — старая схема не переписывается. У HTTP-контракта такого нет: `sim-api` описывает маршруты без номера версии. Первый же клиент, зашитый на текущую форму ответа, станет заложником любого изменения — ровно та ошибка, от которой ядро защитилось.

**Пробел 2. Нет машинно-читаемого описания.** `sim-api` перечисляет маршруты прозой в `spec.md` и типами в `slices.ts`. Клиент на другом языке (Python для анализа, Go для выгрузки) по прозе типы не выведет. Без OpenAPI клиентские типы пишутся руками и расходятся с сервером молча.

**Пробел 3. WebSocket-протокол описан наполовину.** В `sim-api` D6 задан формат сообщения `{ seq, at, type, payload }` и требование монотонного `seq`, но не заданы: набор `type` целиком, поведение при неизвестном типе, лимит журнала и правила закрытия соединения. Клиент не может быть написан против «примерно такого» протокола.

**Что это даёт.** Один контракт, против которого одновременно работают: React-экран руководителя (этап 4), экран цеха для разбора, рабочие места ролей, CLI для прогонов в тестах и внешние выгрузки. UI при этом **не входит** в этот этап — сначала контракт, потом экраны. Причина разделения в `design.md`, D9.

## What Changes

- Появляется версия HTTP-контракта: префикс `/v1/` в пути, номер версии в каждом ответе, правило совместимости.
- Появляется `SIM/api/openapi.json` — единственное машинно-читаемое описание. Схемы выводятся **из существующих типов** `contract/` и `system/`, а не переписываются вручную.
- WebSocket-протокол получает полный реестр типов событий, правила для неизвестного типа и лимит журнала.
- Появляется клиентский пакет с типами (`SIM/api-client/`), годный к публикации внутри репозитория: типы генерируются из OpenAPI, руками не пишутся.
- CORS настраивается явным списком источников, а не `*`.

Не меняется:

- Правило «ядро не знает про транспорт» — `boundary.ts` уже знает зону `api` и запрещает импорт в неё из `plant/`, `system/`, `contract/`.
- Маршруты и решения `sim-api` D1–D8: перепрогон с отсечкой, сессия без состояния цеха, три среза, порт 3400. Этот этап их **не пересматривает**, а достраивает над ними.
- Правила модели производства, ёмкости, `CONTRACT_STAND`, `EXPECTED`.
- Схема событий контракта версии 1 и 2.

## Capabilities

### New Capabilities

- `sim-api-versioning`: версия HTTP-контракта в пути и в теле, правило совместимости, отказ на неподдерживаемую версию.
- `sim-api-description`: `openapi.json` как единственный источник клиентских типов, проверка «описание не разошлось с сервером».
- `sim-api-client`: пакет клиентских типов, сгенерированных из `openapi.json`.
- `sim-api-stream`: полный реестр событий WebSocket, правила неизвестного типа, лимит журнала, поведение при потере соединения.

### Modified Capabilities

- `sim-api`: два пробела, найденных при подготовке этого изменения, — CORS и набор `type` решения. Остальные требования `sim-api` остаются как есть.
