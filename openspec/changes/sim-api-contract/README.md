# Изменение: контракт API для нескольких клиентов

**Этап:** 3b из 5. Зависит от `sim-api` (этап 3a).
**Спецификация игры:** [SIM/README_Game_v1.md](../../../SIM/README_Game_v1.md)

## Зачем это изменение рядом с `sim-api`

`sim-api` отвечает на вопрос «как клиент управляет прогоном». Это изменение отвечает на другой вопрос: **«как несколько разных клиентов живут на одном контракте, не ломая друг друга»**. Ответ — версия, машинное описание, генерируемые типы, полный протокол потока.

React-экраны в это изменение **не входят** (D9): контракт пишется до UI, иначе первый экран продиктует форму данных и второй клиент по ней не построится.

## Замеры, определившие этап

Стенд `clean`/`none`, seed 42, Node v24.13.0:

| Замер | Значение | Что определил |
|-------|----------|---------------|
| 12 перепрогонов (смены 0…11) | 25.9 мс | отказ от кеша (D6) |
| Срез свода на смену | 1.42–1.47 КБ | свод отдельно от цеха (D3) |
| Срез цеха `PlantState` | 11.9–12.1 КБ | цех отдельным маршрутом (D3) |
| Полный отчёт | 10.3 КБ | отчёт не отдаётся целиком |
| Типов в `contract/` и `system/` | 39 + 23 | генерация описания, не ручная (D4) |
| `enum` в strip-only | не поддерживается | запрет `enum` в сервере (D8) |
| Порт 3400 / 5173 | свободны | CORS-список начинается с 5173 (D7) |

## Что этот этап не решает

- **React и экраны** — этап 4 `sim-ui`. Клиентские типы (D5) — доказательство годности контракта для UI, но не сам UI.
- **Аутентификация и роли** — вне целевой архитектуры тренажёра.
- **Остальные семь решений руководителя** — этап 3c.
- **Сохранение сессий в БД** — при требовании, отдельным изменением.
