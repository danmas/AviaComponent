# Изменение: решение «приоритет»

**Этап:** 2.5 из 5. Зависит от `sim-plant-engine`.
**Спецификация игры:** [SIM/README_Game_v1.md](../../../SIM/README_Game_v1.md)

## Зачем этап вставлен перед API

Схема решения в HTTP-контракте без единого работающего решения — угадывание. Это изменение проводит одно решение сквозным путём (вход прогона → очередь цеха → записи → журнал) и даёт этапу 3 готовый формат: `{ batchId, rank, appliedAt }`.

Восемь решений игры в движке отсутствуют: `decision` встречается в `SIM/` только как `quality-decision` контракта и `DecisionRecord` журнала. Проверять нечего, пока нет первого.

## Карта файлов

| Файл | Содержание |
|------|-----------|
| `proposal.md` | Зачем решение вперёд, что входит и что нет |
| `design.md` | Замеры до этапа, решения D1–D5, цена перепрогона |
| `specs/priority-decision/spec.md` | Требования к решению и срезу |
| `tasks.md` | Чекбоксы реализации |

## Ключевые замеры, определившие этап

| Замер | Значение | Что из этого следует |
|-------|----------|----------------------|
| Правка договорной даты `order-4` (10 → 2 смены) | меняет закрытия смен 0–5 | дата — вход модели, решение так делать не может |
| Срез 0 / 5 / 11 смен из финальных записей | 3 показателя из 4 одинаковы | `areaLoads` перезаписывается, срез нужен перепрогоном |
| Полный прогон 12 смен | 0.7–1.2 мс | перепрогон на срез приемлем |
| Префикс 6 смен при горизонте 12 | устойчив | прошлое сохранимо |
| Ранг `batch-3`/`batch-5`/`batch-6` на 5-й смене | прошлое цело, будущее изменилось | решение работает |

## Что этот этап не решает

Остальные семь решений (обещание срока, сверхурочные, кооперация, приём и отложение заявки, проверка данных, приёмка сверх мощности). У каждого своя цена, и переносить их в один этап нельзя: цена требует новых полей в цехе.
