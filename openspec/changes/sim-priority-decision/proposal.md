## Why

Игровой цикл руководителя (решения → смена → последствия → разбор) требует, чтобы решение меняло будущее и **не меняло прошлое**. Замер до этапа: правка договорной даты `order-4` с 10-й смены на 2-ю меняет закрытия в сменах 0–5 — `dueByBatch` задаёт приоритет очереди с нулевой минуты, поэтому любая пост-фактум правка входа переписывает уже случившееся. Разбор «что видел руководитель ↔ что было в цехе» после этого не сходится.

Восемь решений игры в движке отсутствуют: поиск по `SIM/` находит `decision` только как `quality-decision` контракта и `DecisionRecord` журнала. Ни у обещания срока, ни у сверхурочных, ни у приоритета нет места, куда приземлиться. Проектировать схему решения в API без единого работающего решения — угадывание.

Это изменение проводит **одно** решение сквозным путём: смена приоритета. Оно выбрано потому, что `compareReady` уже сортирует очередь по договорной дате, и потому, что его эффект виден в цехе без новых типов ресурсов.

Не меняется:

- Схема событий версии 1, `SIM/contract/`, `SIM/system/`.
- Ёмкости, длительности `ROUTE`, `CONTRACT_STAND`, MTBF.
- Остальные семь решений — этапы 3c и далее.
- HTTP, сессии, WebSocket — этап 3.

## What Changes

- Приоритет становится **рангом, действующим с момента применения**. До `appliedAt` очередь сортируется как раньше.
- Решение пишется в журнал разбора (`DecisionRecord`) с основанием: показатель, его значение, покрытие на момент решения.
- Прогон принимает список решений и возвращает срез на любую границу смены, посчитанный на записях, обрезанных по этой границе.
- Отчёт получает секцию «что видел руководитель» отдельно от «что было в цехе» — без пересчёта прошлого.

## Capabilities

### New Capabilities

- `priority-decision`: одно решение руководителя, действующее вперёд, и срез показателей на границу смены.

### Modified Capabilities

- `plant-engine`: `runShop` получает ранг приоритета с моментом применения; сортировка очереди учитывает момент.
